# Whispr

Whispr is a realtime chat application with registration, sign-in, direct conversations, online presence, typing signals, file uploads, reporting, and a data-backed administration view.

## Run locally

```bash
npm install
npm start
```

Open `http://localhost:3000`. In local development, the first registered account is an administrator. In production, accounts are regular members unless the initial administrator uses the one-time setup token described below. Other users can then be found through the new-conversation search.

## Deploy

Whispr is a Node + Socket.IO application. It cannot be deployed as a Netlify static site because Netlify does not run this long-lived server or its WebSocket process. Deploy the repository to a Node host such as Render, Railway, Fly.io, or a VPS instead.

For Render, create a **Blueprint** from the GitHub repository. The included `render.yaml` supplies the Node build/start commands, generates `JWT_SECRET`, selects Gemini and `gemini-3.5-flash-lite`, leaves `AI_ENABLED=false`, and declares secret slots for `ADMIN_BOOTSTRAP_TOKEN`, `DATABASE_URL`, `GEMINI_API_KEY`, TURN and VAPID credentials. On an existing Blueprint, Render does not update `sync: false` values when you sync the YAML; add/update those secrets in the service's Environment page. Never paste secret values into this repository. Keep AI disabled until the production database and Gemini secret are configured and verified, then deliberately set `AI_ENABLED=true` in the Render service environment.

### Render environment variables

In the Render web service's **Environment** page, verify `NODE_ENV=production` (Render's Node runtime supplies this at runtime), `JWT_SECRET` (the Blueprint generates a 256-bit value), `DATABASE_URL` (the current database's Internal Database URL), and `ADMIN_BOOTSTRAP_TOKEN` (a unique random value of at least 32 characters). Add `GEMINI_API_KEY` as a secret. The Blueprint fixes `AI_PROVIDER=gemini` and `AI_MODEL=gemini-3.5-flash-lite`; keep `AI_ENABLED=false` until `GEMINI_API_KEY` is present and the service has started with PostgreSQL active. Then set `AI_ENABLED=true` only if you want AI enabled for users who separately consent in their profile. To verify provider selection after deployment, inspect the startup log's `AI configuration loaded` line: it should show provider `gemini`, model `gemini-3.5-flash-lite`, endpoint host `generativelanguage.googleapis.com`, and `credentialPresent:true`; it must not include the key. The authenticated `/api/ai/status` endpoint reports provider/model/configuration for the signed-in user.

To configure `DATABASE_URL`, open the PostgreSQL resource in Render, confirm it is in the same region as the web service, and copy its **Internal Database URL** from the database's Connect/Info page into the web service's secret environment value. Do not use the external URL from a Render-hosted app. This repository does not define a Render PostgreSQL resource in `render.yaml`, so the current database URL must be linked manually; do not guess or reuse a URL from logs. Render's Blueprint `sync: false` placeholders are prompted on initial creation only; add new secret values manually to an existing service.

All settings used by the app are: `JWT_SECRET`, `ADMIN_BOOTSTRAP_TOKEN`, `DATABASE_URL`, `DATABASE_SSL` (optional; only set to `true` when the PostgreSQL server requires TLS; this code permits its self-signed certificate), `AI_ENABLED`, `AI_PROVIDER`, `AI_MODEL`, and optional `GEMINI_API_KEY`; for alternate providers selected explicitly, `OPENROUTER_API_KEY` or `OPENAI_API_KEY`; AI tuning values `AI_REQUEST_TIMEOUT_MS`, `AI_MAX_OUTPUT_TOKENS`, `AI_MAX_CONTEXT_MESSAGES`, `AI_CACHE_TTL_SECONDS`, and `AI_DAILY_USER_LIMIT`; optional call relay values `TURN_URL` and `TURN_SHARED_SECRET`; optional complete push configuration `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, and `VAPID_SUBJECT`; optional `TRUST_PROXY_HOPS`, authentication limits `AUTH_RATE_WINDOW_MS`, `AUTH_LOGIN_IP_LIMIT`, `AUTH_LOGIN_ACCOUNT_LIMIT`, and `AUTH_REGISTER_IP_LIMIT`; and optional `UPLOAD_DIR`. Render supplies `PORT` and the Node runtime's `NODE_ENV=production`; the app defaults `TRUST_PROXY_HOPS` to one on Render. `DB_FILE` is only for local JSON storage and should not be used as a production persistence substitute.

`TURN_URL` and `TURN_SHARED_SECRET` must both be configured for relay credentials; without them Whispr only offers STUN and calls may fail across restrictive networks. Push notifications are enabled only when all three VAPID values are present. `VAPID_SUBJECT` should be a contact such as `mailto:admin@example.com` or the site's HTTPS URL. Without all three values, the app reports push as unconfigured.

The current Blueprint uses a Free web service. Render Free web services have ephemeral filesystems and cannot attach persistent disks; this app stores uploaded media files under `uploads/` by default, so media bytes can disappear on restarts/redeploys even though message/file metadata is in PostgreSQL. For durable media, use a paid web service with a persistent disk mounted at the app's uploads directory and set `UPLOAD_DIR` to that mount path, or implement object storage. A production deployment also needs a durable PostgreSQL plan; Render Free PostgreSQL expires after 30 days. Render's plan and storage terms can change, so verify them before choosing a production plan. The app currently assumes one running instance because auth limits, AI quotas/caches, presence, pending calls, and group calls are process-local.

At startup, when `DATABASE_URL` is set, the server creates `whispr_state` if needed, seeds its single JSONB state row for a blank database using the local JSON state currently present (if any), and applies in-code state/group migrations. Once the row exists, PostgreSQL is authoritative. This startup seeding is not a reliable migration plan for data on an ephemeral Render filesystem; verify the source state is present and back it up, or use a controlled import before switching an existing service to a new database. There is no separate migration command or migration directory. The app applies its schema/state/group migrations during startup. Existing admin records remain in persisted state. A blank production database starts with `adminBootstrapUsed=false`; ordinary public registrations remain regular members. Only a registration containing the exact one-time bootstrap token can claim admin, and the token is timing-safe compared, then marked used in the database. Complete the first admin registration privately before public launch, then remove/rotate the token in Render. Do not reset the database or change `adminBootstrapUsed` to recover access; use a reviewed private maintenance procedure.

If the initial admin account is lost, do not reset the application database. Use the host's private service console and a reviewed maintenance procedure to promote the intended account and keep `adminBootstrapUsed` set to `true`; contact the project maintainer if you do not have a safe database maintenance workflow. Never expose database credentials or the setup token in browser code, logs, source control, or support screenshots. Authentication endpoints have temporary IP and account failure limits; proxies should be configured with the correct `TRUST_PROXY_HOPS` value so client addresses are not spoofed or collapsed.

Before deploying a reviewed change, confirm the Render service is connected to the intended repository and branch, check that the deployment's commit SHA matches the reviewed GitHub commit, wait for the health check to pass, then open the service URL and verify sign-in and a synthetic test conversation. This repository's auth limits, AI quotas, presence, pending calls, and group calls are process-local; run a single app instance until those controls and Socket.IO rooms are moved to shared coordination. Do not put a production `DATABASE_URL` in a local test command.

Create a managed PostgreSQL database and set its connection URL as `DATABASE_URL` before considering a deployment production ready. The app stores its application state in a PostgreSQL JSONB record when that setting is present. Without it, the local JSON store remains enabled for development and the server warns that deployed data can be lost.

For calls across restrictive mobile and corporate networks, configure a TURN server such as coturn with its shared-secret REST authentication. Set `TURN_URL` to its `turn:`/`turns:` address and `TURN_SHARED_SECRET` to the server's secret. Whispr creates short-lived TURN credentials for the signed-in user; the long-lived secret stays on the server. Without TURN, some network pairs will not connect even though voice/video permissions and signaling work. On other Node hosts, set `PORT`, `JWT_SECRET`, and `DATABASE_URL` yourself.

## Optional AI features

Whispr's optional AI features use a provider-specific official SDK on the server only. Local development defaults to Google's Gemini API through the official `@google/genai` SDK. Configure `AI_ENABLED=true`, `AI_PROVIDER=gemini`, `AI_MODEL=gemini-3.5-flash-lite`, and the server-only `GEMINI_API_KEY`. Gemini requests go directly to Google's Generative Language API and use JSON-schema structured output. To choose OpenRouter, set `AI_PROVIDER=openrouter`, `OPENROUTER_API_KEY`, and `AI_MODEL=openai/gpt-6-luna`; to choose OpenAI directly, set `AI_PROVIDER=openai`, `OPENAI_API_KEY`, and an OpenAI model ID. Provider selection is centralized, validated, and never borrows another provider's key or falls back to mocked results. Optional controls are `AI_REQUEST_TIMEOUT_MS` (20,000), `AI_MAX_OUTPUT_TOKENS` (700), `AI_MAX_CONTEXT_MESSAGES` (30), `AI_CACHE_TTL_SECONDS` (120), and `AI_DAILY_USER_LIMIT` (30). No AI key is required for normal Whispr chat; without a matching key AI endpoints report unavailable.

Each user must opt into AI processing and select features in their profile. Only the selected message or bounded conversation context needed for that operation is sent to the configured third-party provider. Automatic scam analysis runs only when every member of that conversation has enabled scam analysis. Scam scores are estimates, never proof of fraud or authorization for privileged actions; generated replies remain drafts and are never sent automatically. When Gemini is selected, the [Gemini API terms](https://ai.google.dev/gemini-api/terms) state that unpaid-tier prompts and responses may be used to improve Google products and may be reviewed by humans; do not submit sensitive, confidential, or personal information through that tier. For paid Gemini API service, prompts and responses are not used to improve products, while limited abuse monitoring may still apply. For OpenAI, review its [data controls](https://developers.openai.com/api/docs/guides/your-data). Provider terms and retention vary by provider and account tier.

The AI layer supports smart-reply drafts, automatic/explicit scam assessments, opt-in link safety checks, conversation summaries, translation, draft rewriting, action extraction, and AI-assisted search. Link safety checks are manually triggered from a message's options when the user enables the `linkAnalysis` preference. Whispr inspects up to five HTTP/HTTPS URLs for offline patterns such as unencrypted HTTP, URL shorteners, IP-address hosts, punycode, embedded URL credentials, unusually nested hostnames, risky login/verification path terms, and brand-like hostnames. URL credentials, query-string values, and fragments are redacted before provider analysis. The checker never visits or expands a submitted link and does not query DNS or a live reputation/threat-intelligence database; therefore it is an advisory heuristic, not a malware scan or proof that a URL is safe. Replies are never sent automatically. Daily usage counters and scam findings are stored in the existing application state; short-lived response caches and concurrency guards are process-local, so this design assumes one application process and is not yet safe for horizontal scale. Before adding app instances, move AI single-flight/deduplication and concurrency reservations to a shared atomic store or durable job queue, make quota increments atomic across instances, and share the Socket.IO adapter so private AI result events reach sockets connected to any instance. The broader app also keeps presence, group-call state, and pending calls in process memory, so it needs shared coordination for those before multi-instance operation. Set `AI_ENABLED=false` to disable provider calls.

For local Windows development, create a Gemini API key in Google AI Studio and store it in your Windows user environment as `GEMINI_API_KEY` (or set it only in the current PowerShell process from your approved secret manager). Prefer Google's authorization keys or restrict a standard key to the Gemini API; unrestricted standard keys are rejected by Gemini API. Open a new terminal after changing user environment variables. This app does not load `.env` files; `.env` is ignored by Git, but do not keep keys in a committed file or paste them into source. For direct integration verification, set `RUN_AI_INTEGRATION=true`, `AI_ENABLED=true`, `AI_PROVIDER=gemini`, `AI_MODEL=gemini-3.5-flash-lite`, then run `npm run test:ai-integration`. For OpenRouter or OpenAI, use that provider's matching API key variable. With `AI_PROVIDER` unset, local service and integration tests default to Gemini. The Gemini integration first probes plain-text inference, then a minimal JSON schema, then each Whispr schema/feature; failures report only a sanitized provider code/message, HTTP status, operation, and request ID when available. It suppresses credentials, raw provider bodies, request payloads, and conversation content. Gemini quota/rate-limit, authorization, and model errors are reported without fabricated responses. Provider calls may incur charges; do not use real conversations or sensitive personal data in this test. Leave `RUN_AI_INTEGRATION` unset to skip real calls.

To diagnose OpenRouter authentication separately from model inference, set `RUN_AI_DIAGNOSTICS=true` and run `npm run ai:diagnose`. It makes only a GET request to OpenRouter's key-information endpoint and prints a sanitized status/category, endpoint host, credential-variable name/presence, and request ID when available. It never prints the credential or response body. This diagnostic does not prove that inference/model access works; use the integration test for that. Whispr reads environment variables when the Node process starts and does not load `.env` files, so restart the local server after changing its environment. In PowerShell, environment variables set in one terminal are not automatically inherited by a server running in another terminal.

OpenRouter and direct OpenAI remain supported when explicitly selected with `AI_PROVIDER=openrouter` or `AI_PROVIDER=openai` and their matching server-side key. The Render Blueprint is prepared for Gemini and does not contain any provider key. For privacy, remember that AI requests are sent to the selected third-party provider only for users who opt in; review the provider's terms and applicable account-tier data use before enabling it.

To deliver incoming-call notifications while Whispr is in the background or closed, configure Web Push VAPID credentials: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, and `VAPID_SUBJECT` (a `mailto:` contact or your HTTPS site URL). Generate a key pair with `node --input-type=module -e "import webpush from 'web-push'; console.log(webpush.generateVAPIDKeys())"`, then add the public/private values and subject to the Render environment. Users must press the bell button once on each device/browser to grant notification permission and subscribe. Clicking a call notification opens the app to its incoming-call screen; answering still requires microphone/camera permission. Calls waiting longer than 45 seconds expire.

The chat upload endpoint also blocks a conservative list of executable/active-script file extensions and detects common Windows PE, ELF, and Mach-O executable signatures, including when a binary is renamed with a document extension. This is an upload risk reduction, not antivirus: it does not inspect archive contents, Office macros, scripts hidden in arbitrary data formats, or file behavior. Users should still only open files they trust.

The app stores its runtime data in `data/whispr.json` and uploaded files in `uploads/`; attach persistent storage for both directories in production. These are intentionally ignored by Git so no user content is shipped in the repository.

## Group membership

The group creator is an administrator. Admins can add and remove users from the conversation details panel; any member can leave. Membership updates are persisted and sent to active sockets. Removing or leaving revokes access to history and removes the member from any active group call. Existing groups are migrated on startup by assigning their creator when recorded, otherwise their first existing member, as the initial admin.

## PostgreSQL integration test

The regular test suite never connects to a database. For an explicit isolated persistence test, create a separate blank disposable PostgreSQL database whose name ends in `_test`, then set `RUN_POSTGRES_INTEGRATION=true`, `TEST_DATABASE_URL` to its URL, and `TEST_DATABASE_NAME` to that exact database name in the same PowerShell session. Run `npm run test:postgres-integration`. Before starting the app, the test checks that the URL's host, port, and database are distinct from `DATABASE_URL`, validates the exact designated name and `_test` suffix, and refuses a database with existing application data. It creates uniquely named synthetic accounts and records, does not drop tables, and never deletes existing data. Use a newly created database and credentials with access only to it. Clear the opt-in variables to skip the test. The test verifies startup/schema, CRUD, group membership, read receipts, deletion, reports, profiles, and AI preferences across restart; real AI inference is covered separately by `npm run test:ai-integration`.

## Browser end-to-end test

Install the Playwright browser once with `npx playwright install chromium`, then run `$env:RUN_BROWSER_E2E='true'; npm run test:browser-e2e` in PowerShell. Without `RUN_BROWSER_E2E=true`, Node reports a skipped test with that exact reason. It starts an isolated temporary server on `localhost:3000`, creates synthetic users, launches separate Chromium contexts with fake camera and microphone devices, and removes only its own temporary test directory. Do not start another server on port 3000 while it runs. To exercise all seven real AI features through authenticated browser controls and backend routes, also set `$env:RUN_BROWSER_AI_E2E='true'`, select `AI_PROVIDER` (defaults to `gemini`), provide only that provider's key (`GEMINI_API_KEY`, `OPENROUTER_API_KEY`, or `OPENAI_API_KEY`), and set `AI_MODEL` if needed. The test verifies saved consent/preferences before sending requests and fails on a non-success response. This makes real provider calls and may incur charges. The suite never uses real cameras or microphones.

Uploaded files currently use the `uploads/` directory. Configure a persistent disk for it, or add an object-storage provider before scaling beyond a single persistent server. Serve the application through HTTPS so browsers permit camera and microphone access.
